# 大模型协作与自我纠错记录

本记录整理离线模型与事件算法、FPGA 与 PS–PL 工程交付两个方向的协作过程。两部分分别保留各自的证据口径：算法部分的提示词是依据实际对话整理的代表性表达；FPGA 部分只有明确标为“原句”的内容是直接引用，其余为过程摘要。离线实验、仿真、综合和板端实测分别标识，不以其中一种替代其他结果。

技能使用方法和验证边界见[技能包](../skill/README.md)。

## 一、离线模型与事件算法

下列提示词为原稿依据实际对话整理的代表性表达，模型回答为结论摘要。

### 1. 离线结果与现场识别差异

**问题与提示：** 现场电器与离线测试结果不一致时，要求模型先分析分类混淆、数据来源和采集链，避免立即修改模型。

**纠错与处理：** 现场反馈表明，同名电器可能来自不同设备、采集链和工作状态，不能把离线准确率直接视为现场表现。后续增加设备和采集批次追踪，并先检查标定、特征与采集链。

### 2. 数据处理与划分检查

**问题与提示：** 新增长波形数据需导出固定长度窗口，同时保证旧数据不被重新抽样；同一次采集的窗口不应跨训练集、验证集和测试集。

**纠错与处理：** 模型检查后发现，选择函数虽然存在，主流程仍使用均匀抽样；团队据此核对调用链并保存样本选择清单。划分审查中，用户补充“不同档位下相同 Session 名可能属于不同运行”的事实，修正了模型过粗的分组判断，最终按设备类别、设备、模式和 Session 识别采集单元。

### 3. 冻结模型与未知负载接入

**问题与提示：** 接入未知负载拒识后，要求模型说明何时运行 CNN，以及 KNN 和 Gate 在最终流程中的作用。

**纠错与处理：** 早期“仅困难样本运行 CNN”的解释与拒识需要64维深度特征相矛盾。整理后区分“CNN 前向计算”和“CNN 分类结果参与闭集仲裁”：有效身份判断需取得深度特征，Gate 继续参与闭集候选判决。模型权重、特征缩放、类别映射和黄金样本输出需分别核对。

### 4. 多电器事件与残差验证

**问题与提示：** 要求事件检测只依据电压、电流变化，不能使用电器标签或分类结果选择事件及残差信号。

**纠错与处理：** 高召回候选中存在重复、启动瞬态和微小变化，后续将持续状态验证与候选检测分开；含糊的相邻事件保守处理。残差信号先按物理规则选择，再送入冻结分类器，真实标签只用于事后评价。上述 V5、V5.2 和 V5.4 为离线开发过程，应与最终板端实现分别核对。

### 5. 工程交接与可复现

**问题与提示：** 多人交接中不能仅凭文件名判断版本，需检查依赖、冻结资产及结果是否一致。

**处理与验证：** 依据原记录，团队沿脚本依赖检查输入、配置、模型和环境，并通过文件哈希、类别映射及黄金输入输出进行回归核对。由此提炼出数据划分审查、冻结模型回归和事件管线验证三项 Skill；各项的实际验证范围和失效条件见[技能包说明](../skill/README.md)。

## 二、FPGA 与 PS–PL 工程交付

来源：工程包 `report/ai_collaboration.md`。仅标为“用户原句”或“模型回应原句”的内容为直接引用；其余为过程摘要或验证材料索引。



### 需求如何转成实现边界

用户原句：“演示页面只是进行展示数据的，不是用来计算的，要搞清楚，要充分发挥PL端加速的功能，再到后面的模型自学习进程”。

过程摘要：将 CNN 特征计算留在 PL，事件、拒识、登记和计量留在 PS，电脑桥接只展示并发送操作。后来用户明确“先不做神经网络自训练”，因此当前登记流程只增补参考库，没有把登记包装成神经网络权重更新。对应 src/hls、src/ps、src/web。

用户原句：“做吧。记得登记电器这个内容，登记了新电器后会一直保存，额能不能加一个清空的按钮，用来删除登记内容，不然以后如果登记错了也没有解决方案”。

过程摘要：保存、删除与清空必须作为同一状态一致性问题处理；不仅删除页面条目，还要写 SD、更新库版本、作废匹配缓存并保护其他配置。对应 test_store.c、test_registration.c 和网页控制接口。

### 故障拆分与验证

用户原句：“两类故障分别是：”并在后续描述中分别指出 SOURCE_UNSTABLE 和 AUXILIARY_UNKNOWN_EXPOSURE。

过程摘要：前者属于事件波形提取或稳定性，后者属于已经进入判断后的未知/登记路径，不能都用“样本不够”解释。诊断需要保留背景/后侧窗口、阈值、最近参考距离、拒绝原因与计量恢复取消原因。旧日志在 data/field_logs，回归验证在 sim/results；回归通过仍需现场复验，不把旧现场失败直接标成修复验收通过。

### 本次打包中的可审计纠错

| 观察 | 修正 | 验证证据 |
|---|---|---|
| 协同仿真平均周期包含快速失败请求 | 使用有效长事务 2,924,558 周期，不使用混合平均 | build/reports/performance |
| 平台目录过长导致 Windows 编译失败 | 缩短为 work/vitis_short/p；脚本显式检查库和 FSBL，避免 SDK 返回而误报成功 | build/create_platform.py、platform_build.json |
| 硬件源 XCI 的旧生成路径影响独立重建 | 使用 import_ip 将 IP 导入新工程，按包内相对路径引用 | create_hardware.tcl、hardware_recreate.log |
| C 回归依赖作者原目录 | 将模型源、桩文件、黄金输入放到包内，调整测试路径 | build/test_host.ps1、sim/results |
| 原运行包校验清单包含未复制文件 | 对最终实际文件重新生成校验清单，同时单独核对原 BOOT/EXE 一致性 | checksums.json、delivery_identity.json |

本轮模型回应原句：“板端应用编译和 BOOT 生成也通过了。包内会保留原来配套的运行文件，并附上这次重建的验证记录；性能部分明确区分理论倍率、仿真延迟和未实测项目，报告与 Skill 正在做最后整理。”

### 提炼出的 Skill

1. 接口契约：版本、形状、模型、地址、缓存和中断现场必须一起检查，不能只看数值样例。
2. 分阶段定位：采样、事件、基础分类、登记匹配、计量分别收集证据。
3. 数值比对：形状与字段先匹配，再用绝对和相对误差比较，并拒绝 NaN。
4. 交付校验：检查路径范围和散列，区分源文件编译通过、仿真通过、板上验收。

脚本包含正反向自测，使用方法和失效条件见 skill/README.md。技能范围是 Zynq 裸机 PS/PL 工程验证；没有验证 PYNQ Overlay、Linux 驱动或跨板卡自动迁移。
